# 原材料仓非感应式货架方案讨论

## 1. 背景与目标

原材料仓当前使用非感应式智能货架完成入库和出库作业。现有流程能够通过亮灯引导具体库位，但对扫码次数、库位确认和现场摆放规则依赖较高。

本次讨论的目标是：

- 降低原材料仓入库扫码次数。
- 保留出库 FIFO（先进先出）和可超需求发料规则。
- 在不引入感应式货架硬件的前提下，评估通过“大库位”方式优化现有出入库逻辑的可行性。
- 明确大库位模式下条码、库位、批次、盘数和库存数量之间的数据口径。

## 2. 当前系统已实现流程

### 2.1 当前入库流程

1. 扫描起始库位号。
2. 系统自动识别所属料架。
3. 扫描条码（托盘码/料盘码）。
4. 系统点亮对应空库位。
5. 仓管员按照约定规则放入货架。
6. 扫描确认库位，完成入库。

> 约定规则：从起始库位开始，料盘序号最小的放第一个位置，次小序号的放第二个位置，依次类推。

### 2.2 当前出库流程

1. 扫描领料单。
2. 系统计算物料需求量。
3. 系统查询满足条件的物料条码。
4. 系统点亮对应条码所在库位。
5. 仓管员拿出全部亮灯条码。
6. 点击“拣货完成”。

出库规则：

- 按 FIFO（先进先出）分配。
- 允许超需求发料。
- 不拆料，不要求精准凑满需求数量。

## 3. 现有流程痛点与扫码次数

### 3.1 假设入库数据

| 项目 | 数量 |
| --- | ---: |
| 料盘 | 100 盘 |
| 托盘 | 10 托 |
| 每托包含条码 | 10 个 |

### 3.2 当前入库扫码次数

| 操作方式 | 扫码次数 |
| --- | ---: |
| 全扫料盘 | 库位号 100 次 + 条码 100 次 + 确认库位号 100 次 = 300 次 |
| 全扫托盘 | 库位号 10 次 + 托盘 10 次 + 确认库位号 10 次 = 30 次 |

### 3.3 当前出库扫码次数

| 操作 | 扫码次数 |
| --- | ---: |
| 扫描领料单 | 1 次 |

### 3.4 评审口径说明

本文档中的候选改造方案共有 2 种：

- 方案一：换用感应式货架。
- 方案二：原材料仓大库位按盘数量账方案。

如果将当前系统已上线的精确小库位流程一并纳入评审，则本次实际对比对象共有 3 种出入库模式：

- 模式 A：现有精确小库位模式。
- 模式 B：感应式货架模式。
- 模式 C：大库位按盘数量账模式。

以下评审结论统一基于当前系统已支持“托盘码优先、真实库位分配、二次确认”的前提，并假设原材料仓主流作业场景以整托入库为主、每盘数量大多固定，但仍需保留异常处理空间。

## 4. 方案一：换用感应式货架

### 4.1 入库流程

1. 扫描料架。
2. 扫描条码。
3. 放入料盘。
4. 等待系统确认。
5. 确认入库完成。

假设入库数据为 100 盘料，则扫码次数为：

| 操作 | 扫码次数 |
| --- | ---: |
| 扫描库位号 + 扫描条码 | 100 次 + 100 次 = 200 次 |

### 4.2 出库流程

1. 搜索需要出库的条码（按料号）。
2. 选择出库条码。
3. 系统点亮条码所在库位。
4. 仓管员拿出料盘。

| 操作 | 扫码次数 |
| --- | ---: |
| 出库扫码 | 0 次 |

### 4.3 方案评价

感应式货架能够减少出库扫码，并通过硬件感应确认库位状态。但该方案需要更换或新增硬件，实施成本和改造周期较高，不属于本次“修改现有非感应式出入库逻辑”的主推方向。

综合来看，方案一的优劣势如下：

- 优势：系统与实物位置一致性最高，库位确认能力最强，出库作业动作最顺。
- 劣势：需要新增或更换硬件，实施成本、改造周期和后续维护复杂度最高，不符合本次“不引入感应式货架硬件”的边界。
- 适用判断：属于理想方案，但不属于本次讨论范围内的优先落地方向。

## 5. 方案二：原材料仓大库位按盘数量账方案

### 5.1 核心思路

将多个真实小库位合并为一个“大库位”。系统不再追踪某个具体条码实际进入哪个小库位，而是维护该大库位下某个料号、批次占用了多少盘，以及每盘代表多少数量。

大库位模式下：

- 扫描条码只用于定位料号、批次、仓库，不代表扫描的条码一定被实际放入货架。
- 仓管员可以从同料号、同批次物料中随机抽取料盘放入大库位。
- 大库位内一个空位对应一个盘位，盘位被占用后即代表该盘物料已经进入该大库位。
- 系统不知道具体哪一盘实物进入了哪个小库位，因此不修改条码的 `BinNo`。
- 大库位库存表是位置和数量的可信来源。
- 同料号、同批次条码的 `IsRack` 只作为盘数状态依据，用于表示该批次已经入库了多少盘、还有多少盘未入库，不作为具体位置依据。

### 5.2 数据口径

| 数据对象 | 维护内容 | 说明 |
| --- | --- | --- |
| 大库位主数据 | 大库位码、所属仓库、关联真实小库位、总容量、删除标记 | 小库位用于扫码反查大库位和亮灯范围；绑定的小库位数量作为大库位理论容量依据 |
| 物料标准盘数量配置 | 料号、每盘标准数量 | 例如某物料每盘默认 5000 |
| 大库位库存账 | 大库位码、料号、批次、占用盘数、每盘数量、总数量、入库时间、状态 | 作为大库位位置和数量的核心库存记录 |
| 条码明细 | `IsRack` 批次盘数状态 | 同料号、同批次下，`IsRack='Y'` 表示该批次已有对应盘数计入在架，`IsRack='N'` 表示该批次还有对应盘数未入库；只用于盘数统计，不修改 `BinNo` |

### 5.3 大库位与小库位关系

大库位内部仍需要维护真实小库位码，但用途发生变化：

- 用于扫描任意小库位时反查所属大库位。
- 用于系统亮灯时点亮大库位范围。
- 用于计算大库位总容量。

大库位模式不要求维护每个小库位具体放了哪一盘料。系统只关心大库位还有多少空位、每个空位可承载多少数量，以及当前大库位内已经占用了多少盘。

扫描小库位后，大库位剩余空位的判断规则建议明确为：

1. 根据扫描到的小库位反查所属大库位。
2. 以 `大库位码 + 删除标记 = N` 查询大库位库存账。
3. 对该大库位库存账中的 `占用盘数` 进行聚合，得到当前已占用盘数。
4. 统计该大库位当前绑定的小库位数量，作为该大库位理论可用盘位数。
5. 将“已占用盘数”与“绑定小库位数量”比较，得到入库判定：

   ```text
   已占用盘数 < 绑定小库位数量  => 还有空位，允许入库
   已占用盘数 = 绑定小库位数量  => 大库位已满，不允许继续入库
   已占用盘数 > 绑定小库位数量  => 非法状态，通常表示大库位与小库位绑定关系发生过变更
   ```

在“允许入库”的情况下，大库位剩余空位数计算为：

```text
大库位剩余空位数 = 绑定小库位数量 - 已占用盘数
```

### 5.4 入库流程

1. 扫描样本条码。
2. 系统根据样本条码查询料号、批次、仓库。
3. 系统根据同料号、同批次条码中 `IsRack='N'` 的数量，查询该批次还有多少盘未入库。
4. 扫描大库位内任意真实小库位。
5. 系统反查对应大库位，并以 `大库位码 + 删除标记 = N` 查询大库位库存账。
6. 系统对该大库位库存账的 `占用盘数` 进行聚合，并与该大库位绑定的小库位数量比较，判断是否允许入库：

   ```text
   聚合占用盘数 < 绑定小库位数量  => 允许入库
   聚合占用盘数 = 绑定小库位数量  => 大库位已满，不允许入库
   聚合占用盘数 > 绑定小库位数量  => 非法状态，提示检查大库位绑定关系
   ```

7. 系统计算本次可入库盘数：

   ```text
   本次可入库盘数 = min(同批次待上架盘数, 大库位剩余空位数)
   ```

8. 系统在允许入库时提示该大库位还能入几盘，并显示料号、批次、盘数和每盘数量。
9. 仓管员从该料号、该批次物料中随机抽取对应盘数放入大库位。
10. 仓管员确认入库。
11. 系统新增大库位库存记录，并同步更新聚合占用盘数结果。
12. 系统按 `BarNo` 升序选择相同批次、相同盘数且 `IsRack='N'` 的条码，仅将 `IsRack` 修改为 `Y`，不修改 `BinNo`。
13. 系统根据该批次剩余 `IsRack='N'` 的条码数量，提示剩余未入库盘数。

### 5.5 `IsRack` 盘数口径说明

在大库位模式下，`IsRack` 的含义需要与普通精确库位模式区分开来：

- 对同料号、同批次而言，`IsRack='Y'` 表示该批次已有对应盘数被计入在架状态。
- 对同料号、同批次而言，`IsRack='N'` 表示该批次还有对应盘数未入库，可继续参与上架计算。
- `IsRack` 在大库位模式下是盘数状态字段，不是实物条码与具体小库位的一一对应关系。
- 因此，先扫描任意一个样本条码时，系统实际带出的不是“这一个条码是否已上架”，而是“这个批次当前还有多少盘未入库”。

### 5.6 入库示例

大库位有 5 个空位，同料号、同批次共有 10 盘待入库。

| 项目 | 数量 |
| --- | ---: |
| 大库位剩余空位 | 5 个 |
| 同批次待入库数量 | 10 盘 |
| 本次可入库数量 | 5 盘 |
| 入库后该批次剩余待入库 | 5 盘 |

系统只记录该料号、该批次有 5 盘进入该大库位，不记录具体哪 5 个条码或哪 5 盘实物进入了该大库位。

如果某个大库位绑定了 5 个小库位，而库存账聚合后的占用盘数为：

- 4 盘：说明还剩 1 个空位，允许继续入 1 盘。
- 5 盘：说明该大库位已满，不允许继续入库。
- 6 盘：属于非法状态，应优先检查大库位绑定的小库位关系是否发生过变更或历史数据是否异常。

### 5.7 同批次重复入库处理

如果后续相同料号、相同批次的物料再次入库到同一个大库位，建议新增一条大库位库存记录，不合并更新原记录。

原因：

- 保留每次入库时间，便于 FIFO。
- 保留每次入库数量，便于追溯。
- 避免合并后丢失真实作业批次。

### 5.8 入库侧综合评审

从入库角度看，大库位方案的主要优势在于：

- 适合同料号、同批次、整盘、不拆盘的大批量上架场景。
- 可以放宽对精确小库位摆放顺序的依赖，降低现场逐盘定位压力。
- 在逐盘入库占比较高时，扫码次数有机会明显低于现有精确小库位模式。

其主要代价也需要同时明确：

- 牺牲了条码级位置真实性，条码 `BinNo` 不再代表真实货架位置。
- 系统必须依赖独立的大库位库存账，而不能再用旧逻辑直接按条码位置解释库存。
- `IsRack` 只能作为同批次已入库盘数和剩余未入库盘数的状态依据，不能再被解释为某个具体实物条码的精确位置状态。
- 扫码收益主要出现在逐盘作业场景；如果现场以整托入库为主，则不一定比现有流程更省扫码。
- 一旦出现非标准盘、拆盘、尾盘或回库场景，就需要单独设计异常处理，而不能完全沿用标准盘逻辑。

## 6. 推荐出库业务逻辑

### 6.1 出库盘数计算

原材料仓大库位模式按整盘发料，不拆盘。每盘数量来自物料固定配置，一个盘位对应一盘物料。

```text
应发盘数 = ceil(领料需求数量 / 每盘标准数量)
实际发料数量 = 应发盘数 * 每盘标准数量
```

示例：

| 项目 | 数量 |
| --- | ---: |
| 领料需求数量 | 9000 |
| 每盘标准数量 | 5000 |
| 应发盘数 | 2 盘 |
| 实际发料数量 | 10000 |

该示例中实际发料数量超过需求数量，符合“可超需求发料、不拆盘”的现有出库规则。

### 6.2 出库流程

1. 扫描领料单。
2. 系统根据领料单查询需求物料和需求数量。
3. 系统根据物料标准盘数量计算应发盘数。
4. 系统从大库位库存账中按入库时间 FIFO 查询可发记录。
5. 系统返回料号、批次、大库位、应发盘数、每盘数量和实际发料数量。
6. 系统点亮对应大库位关联的真实小库位范围。
7. 仓管员按系统提示核对料号和批次，并从亮灯大库位取出对应盘数。
8. 点击“拣货完成”。
9. 系统扣减大库位库存账中的占用盘数，并释放大库位空位。
10. 系统按数量镜像规则选择对应数量的 `IsRack='Y'` 条码改回 `N`，使其重新反映该批次当前仍有多少盘在架。

### 6.3 跨大库位出库示例

某物料需要出库 7 盘，库存分布如下：

| 大库位 | 批次 | 入库时间顺序 | 当前库存 |
| --- | --- | ---: | ---: |
| LL01 | B001 | 1 | 5 盘 |
| LL02 | B001 | 2 | 5 盘 |

出库时按 FIFO：

1. 先从 LL01 发 5 盘。
2. 再从 LL02 发 2 盘。

这样可以保持系统大库位库存账与现场实物出库顺序一致。

### 6.4 出库侧综合评审

从出库角度看，大库位方案能够保留“FIFO、整盘发料、允许超需求发料”的核心业务目标，但其 FIFO 口径发生了变化：

- 现有精确小库位模式下，FIFO 更接近条码级、可定位、可验证的 FIFO。
- 大库位模式下，FIFO 变为“大库位库存账 FIFO + 现场核对”的组合控制。

因此，大库位方案的优势与限制分别为：

- 优势：仍可按入库时间顺序优先消耗较早入库批次，并保留亮灯指引和整盘发料能力。
- 劣势：如果现场在同一大库位内混放批次、摆放无序，系统虽然账上仍可 FIFO，但现场执行难度会明显上升。
- 控制要求：出库时必须按系统提示核对料号、批次和大库位顺序，不能再把条码 `BinNo` 当作精确拣货位置依据。

## 7. 扫码次数对比

### 7.1 大库位方案假设数据

| 项目 | 数量 |
| --- | ---: |
| 料盘 | 100 盘 |
| 托盘 | 10 托 |
| 每托包含条码 | 10 个 |
| 批次 | 5 个 |
| 每批次托盘数 | 2 托 |
| 大库位规则 | 5 个真实小库位合并为 1 个大库位 |

### 7.2 大库位入库扫码次数

最好情况：所有大库位都为空，每次可入库 5 盘。

| 操作方式 | 扫码次数 |
| --- | ---: |
| 全扫料盘 | 扫库位码 20 次 + 扫样本条码 20 次 = 40 次 |
| 全扫托盘 | 扫库位码 20 次 + 扫托盘/样本码 20 次 = 40 次 |

最坏情况：所有大库位都只剩 1 个空位，每次只能入库 1 盘。

| 操作方式 | 扫码次数 |
| --- | ---: |
| 全扫料盘 | 扫库位码 100 次 + 扫样本条码 100 次 = 200 次 |
| 全扫托盘 | 扫库位码 100 次 + 扫托盘/样本码 100 次 = 200 次 |

### 7.3 大库位出库扫码次数

| 操作 | 扫码次数 |
| --- | ---: |
| 扫描领料单 | 1 次 |

以上对比说明，大库位方案的扫码优化主要集中在逐盘上架场景；若现场主流作业本身以整托入库为主，则现有精确小库位流程在扫码次数上未必处于劣势。

## 8. 与现有出入库逻辑的关系

大库位按盘数量账方案不建议直接替换所有普通非感应式流程，而应作为原材料仓的独立模式启用。

### 8.1 保留现有逻辑

以下流程保持不变：

- 普通非感应式入库：继续按真实库位更新条码 `BinNo`。
- 普通非感应式出库：继续按条码所在真实库位亮灯。
- 感应式入库和出库：继续依赖感应式货架回调确认。

### 8.2 新增大库位逻辑

原材料仓大库位模式单独维护：

- 大库位主数据。
- 物料标准盘数量配置。
- 大库位库存账。
- 大库位入库和出库接口。
- 大库位亮灯范围。

同时需要强化以下隔离原则：

- 现有普通非感应式流程继续按真实 `BinNo` 和条码位置运行。
- 大库位模式下，条码 `BinNo` 不再代表真实货架位置，旧拣货逻辑不能直接复用来解释大库位条码位置。
- 大库位出入库、亮灯、库存扣减和状态回写必须优先以大库位库存账为准，而不是以条码 `BinNo` 为准。

## 9. 待确认事项与风险

### 9.1 待确认事项

| 事项 | 当前建议 |
| --- | --- |
| 每盘数量来源 | 采用物料固定配置 |
| 同批次同料号再次入库 | 新增大库位库存记录，不合并 |
| 条码 `BinNo` | 大库位模式不修改 |
| 条码 `IsRack` | 作为同批次盘数状态依据，表示已入库盘数和剩余未入库盘数，不表示精确位置 |
| 出库方式 | 按整盘向上取整，可超需求发料 |
| 小库位占用 | 不维护精确占用；通过大库位库存账聚合占用盘数，并与绑定小库位数量比较后判断剩余空位 |

### 9.2 主要风险

| 风险 | 说明 | 控制方式 |
| --- | --- | --- |
| 条码身份与实物不一一对应 | 随机放料后，系统无法知道具体哪盘实物上架 | 明确大库位模式按批次和盘数管理，不按具体条码定位 |
| 旧逻辑误用 `BinNo` | 大库位模式下 `BinNo` 不代表货架位置 | 大库位出库必须使用大库位库存账，不能按条码 `BinNo` 查位置 |
| 超需求发料 | 按整盘出库可能超过领料需求 | 界面显示需求数量、应发盘数和实际发料数量 |
| 现场批次混放 | 大库位内如果批次摆放混乱，会影响 FIFO | 出库时要求核对料号和批次，并按系统提示的大库位顺序取料 |
| 数据一致性 | 大库位库存账、剩余空位、`IsRack` 数量镜像可能不一致 | 入库确认和拣货完成必须在事务内同步更新 |
| 大库位绑定关系变更 | 如果绑定小库位数量变小，而库存账聚合占用盘数未同步调整，可能出现占用盘数大于容量 | 当聚合占用盘数大于绑定小库位数量时，直接判定为非法状态并禁止继续入库，提示检查绑定关系和历史数据 |

## 10. 推荐结论

综合业务作业和系统合理性，推荐结论分为以下三个层次：

### 10.1 整体最优结论

现有精确小库位流程应继续作为原材料仓主流程。

原因是：

- 当前系统已经支持托盘码优先、真实库位分配和二次确认，条码、库位、库存和亮灯逻辑口径一致。
- 在原材料仓主流作业以整托入库为主的前提下，现有流程的扫码成本并不一定高于大库位方案。
- 现有流程保留了条码级位置真实性，FIFO、锁定、亮灯和出库完成逻辑都更容易保持一致。

### 10.2 改造方案中的更现实选择

若只在两个改造方案中二选一，方案二“大库位按盘数量账方案”比方案一“感应式货架方案”更现实。

原因是：

- 方案一虽然在系统与实物一致性上更理想，但硬件成本和改造周期较高，不符合本次约束。
- 方案二不需要新增感应硬件，能够在现有非感应式货架基础上做业务口径调整。
- 方案二更适合用于解决原材料仓中部分逐盘上架、整盘发料、不拆盘场景的作业痛点。

### 10.3 方案二的建议落地方式

方案二不建议直接替代现有普通非感应式流程，而更适合作为原材料仓独立试点模式。

建议仅在以下条件同时成立的作业区优先试点：

- 逐盘上架痛点明显。
- 以整盘发料为主，不拆盘。
- 每盘数量相对稳定。
- 现场能够维持按料号、批次的基本摆放纪律。

在该前提下，方案二的关键管理口径应明确为：

```text
大库位 + 料号 + 批次 + 盘数 + 每盘标准数量
```

该模式的价值在于放宽精确小库位管理要求，并保留 FIFO、整盘发料和大库位亮灯指引能力；其代价是放弃条码级精确位置追踪，因此只能作为与现有流程并行隔离的独立模式使用。
